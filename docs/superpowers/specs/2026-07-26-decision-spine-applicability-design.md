# Decision spine + applicability — дизайн

Дата: 2026-07-26. Статус: утверждён пользователем (brainstorming-сессия), реализуется.

## Проблема

Внешняя критика прогонов скилла (читатель отчётов): «доки неприменимы — изначальные
задачи для ИИ неверные, автор не знает, что спрашивать, чтобы ответ потом к чему-то
привёл». Диагноз: решение, которое ресёрч должен поддержать, фиксируется один раз
строчкой в Фазе 1 и дальше нигде не проверяется. Жанр выбирается по теме, синтез — по
блокам, acceptance criteria — про отчёт, а не про решение. Отчёт закрывается зелёным
gate'ом и умирает непримененным.

Вторая половина проблемы — качество самого поиска: механическое правило триангуляции
(≥3 источника, ≥2 типа) не проверяет независимость первоисточников (circular
reporting), цепочки цитирований не проходятся систематически, язык/операторы запросов
не мутируют между раундами, остановка поиска бинарна (no-progress breaker), а не
градуальна (насыщение).

## Решение: decision-first spine

Решение проходит через все фазы как проверяемый артефакт; в конце оно не
«обсуждается», а исполняется. Плюс четыре усиления поискового контура.

### Вход (Фаза 1 + 3.7)

1. **Decision Spec** — структурный мини-контракт в plan.md §0, три обязательных поля:
   - *Решение/действие*: глагол + объект + срок. Не «понять тему».
   - *Потребитель и следующий шаг*: кто читает и что физически делает после.
   - *If-then вилки*: ≥1 опровергаемая — «покажет X → делаю A; Y → делаю B».
   Нет ни одной вилки ⇒ ресёрч ничего не изменит ⇒ честный даунгрейд в shallow
   «любопытство» с явной пометкой. Расплывчатый ответ (нет глагола/артефакта/срока)
   → один push-back, дальше допущение с пометкой «применение — гипотеза агента».
2. **Plan-review gate (3.7)** показывает Decision Spec первой строкой — пользователь
   утверждает «зачем и что сделаю с ответом», а не только «что ищем».
3. **Жанр (Фаза 2)**: форма = функция процесса потребителя, не типа темы.

### Поиск (Фазы 4–5)

- **S1 Provenance-триангуляция.** Fetch-агент заполняет `root:` во frontmatter
  источника (на чём источник основан: пресс-релиз X / исследование Y / own).
  Правило Фазы 5: `triangulated` требует ≥2 различных корней; иначе новый статус
  `single-root`, confidence ≤ medium. Закрывает circular reporting механически
  (раньше — только предупреждение прозой в source_scoring.md).
- **S2 Snowball-пасс.** После Round 1 (medium/deep): топ-K источников по total
  (K=2 medium / 3 deep) → backward (их ссылки → канонические primary вне пула) +
  forward (кто цитирует, через OpenAlex/Semantic Scholar из api_sources/academic).
  Плановый шаг цикла, не deviation. Систематизирует существующий тригger
  `citation_lead`.
- **S3 Query-мутации.** Суб-агент возвращает `query_performance` (какие формулировки
  дали used-источники, какие — шум); межраундовый eval мутирует запросы следующего
  раунда: RU↔EN, операторы (site:, filetype:pdf, точные фразы, даты), терминология
  практиков vs академическая.
- **S4 Saturation-метрика.** Novelty rate раунда = доля новых entities/claims против
  известных. Ниже порога (~20%) — сигнал насыщения в eval и деградация к остановке;
  пишется в deviations.md. Градуальное дополнение к бинарному circuit breaker.
- Мелочь: `as_of` для волатильных чисел в claims.csv.

### Выход (Фазы 6 и 8)

- **A1 Decision memo** — `memo.md`: одна страница, входящая в процесс потребителя:
  рекомендация, разрешённые вилки, 3 ключевых числа с [sNN], главный риск, next
  actions. Отчёт = доказательная база под меморандумом. Обязателен всегда (в shallow
  крошечный). Артефакт Фазы 6.
- **A2 Запрет финала «it depends».** Если однозначная рекомендация невозможна —
  обязана быть условная, замапленная на вилки Decision Spec. «It depends» без
  разрешённых условий = незакрытый acceptance criterion.
- **A3 Роль R4 «Исполнитель»** в red team (Фаза 6): агент играет потребителя из
  Decision Spec и пытается исполнить решение, пользуясь только отчётом; каждый затык
  (нет числа, нет рекомендации, hedge-язык) — finding. Включает hedge-линт по списку
  фраз («может помочь», «стоит рассмотреть», «в некоторых случаях») на memo и TL;DR.
  Гейт: medium = R1+R2+R4, deep = R1+R2+R3+R4.
- **Z12 привязывается к Decision Spec**: ключевые claims мапятся на вилки/критерии;
  applicability ratio = замапленные/все (дескриптивная метрика в rubric, не весовая
  ось). Незамапленные claims — флаг «зачем в отчёте?».
- **Фаза 8 Decision walkthrough** (новая, depth_gate shallow — обязательна всегда;
  модель opus/high). НЕ Q&A о применимости, а исполнение: агент ведёт пользователя по
  вилкам по одной («ресёрч показал X [s03][s11] — вилка A срабатывает? выбор?»).
  Исходы на вилку: решение принято / заблокировано данными (→ одна целевая gap-волна,
  max 1 круг, повторный заход) / отложено (`status: deferred` — честно, без дожима).
  Артефакт `application.md`: снимок Decision Spec, вердикт по вилкам, решения, next
  actions, applicability ratio, неиспользованные claims. Gate требует существования
  файла со статусом, НЕ принятого решения (автопрогоны не блокируются на человеке).
- **Ledger между ресёрчами**: `~/.claude/research/applications_ledger.csv`
  (slug, дата, spec есть?, статус applied/deferred/unused, ratio). Фаза 1 следующего
  ресёрча читает ledger и показывает паттерн непримененных прогонов.

## Enforcement (философия: неисполняемый абзац умирает)

| Правило | Машинный крюк |
|---|---|
| `root:` заполнен | build_sources_csv.py — колонка root |
| ≥2 корней для triangulated | механика Фазы 5 (правило в workflow.md) |
| memo.md существует | validate_phases.py — артефакт Фазы 6 |
| application.md существует (любой status) | validate_phases.py — артефакт Фазы 8 |
| applicability ratio, novelty rate | eval/rubric.md — дескриптивные метрики |
| hedge-линт | часть промпта роли R4 (без отдельного скрипта в этой волне) |

## Out of scope

- Follow-up «через N дней спросить, применил ли» — навязчиво, ledger дешевле.
- Запись ответов walkthrough в сам отчёт — application.md рядом чище.
- Новая весовая ось в SCORE_CONFIG / правки score_run.py — applicability ratio
  дескриптивен в этой волне.
- Отдельный скрипт hedge-линта — сначала обкатать список фраз в роли R4.
