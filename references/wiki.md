# Вики — кросс-прогонный слой знания

Читать: перед `discover existing` (чтение) и в фазе 5.7 (сверка). Запись — в finish-up, руками ничего не редактируется.

## Зачем

У скилла было два слоя из трёх. **Raw** — `sources/NN.md` в прогоне и `~/.claude/deepdive-state/observations.jsonl`. **Skills** — `references/channels.md` и `api_sources/`, которые правит `promote_candidates.py` за честным гейтом (3 победы в 3 РАЗНЫХ прогонах + живой endpoint + демоушен по DEAD_STRIKES). Между ними не было ничего, и последствие простое: накапливалось знание **где искать**, но не **что выяснено**.

Что из этого следовало:

- один источник в двух ресёрчах — два несвязанных файла, credibility считается с нуля;
- claim, триангулированный в июне, невидим прогону в августе;
- два прогона могут прийти к противоположным выводам, и этого никто не заметит;
- `application.md` со статусом `deferred` списывал прогон целиком.

Вики закрывает именно это. Она переживает отклонение отчёта: знание отделено от вердикта по нему.

## Где лежит

`~/.claude/research/wiki/` — глобально, не в папке проекта. Ресёрч-папки живут по проектам (`research/`, `06_Деск-ресёрч/`, `~/deep-research/`), и вики внутри проекта раздробила бы ровно то, что должно накапливаться. Прецедент уже есть: `applications_ledger.csv` и `deepdive-state/` тоже глобальные.

```
wiki/
├── INDEX.md              # навигация, перегенерируется каждым ingest
├── sources/<slug>.md     # одна страница = один канонический URL/DOI
├── entities/<key>.md     # компания / инструмент / метод
├── claims/<c-id>.md      # одно НАБЛЮДЕНИЕ утверждения (прогоны не сливаются)
└── .wiki/
    ├── sources.csv · entities.csv · claims.csv   # реестры, из них рендерятся страницы
    └── pairs.jsonl                               # вердикты по парам, append-only
```

## Три ключа джойна — и почему третий устроен иначе

| Слой | Ключ | Природа |
|---|---|---|
| Источники | канонический URL, DOI важнее URL | механический |
| Сущности | свёрнутое имя + алиасы | полумеханический |
| Утверждения | `(run, claim_id)` — **не текст, не смысл** | наблюдение, не сущность |

Источники сливаются автоматически: `arxiv.org/abs/X`, `/pdf/X`, `/html/Xv2` — одна страница. Отваливаются схема, `www.`, utm-параметры, фрагмент, хвостовой слэш.

Утверждения **не сливаются никогда**. Решить, что две фразы из разных прогонов — «одно и то же утверждение», это смысловое суждение, и ошибка в нём производит противоречие из ничего: сломанный замер → ложный диагноз. Поэтому идентичность claim'а здесь не выводится. Есть только рёбра между наблюдениями, каждое с вердиктом и следом в `pairs.jsonl`. Ошибочное ребро — одна строка на починку; ошибочное слияние необратимо.

`claim_uid = (run, claim_id)` намеренно **не включает текст**: 5.7 строит пары до синтеза, ingest пишет после, а между ними формулировку правят (ремедиация, возвращённая оговорка, смягчённый overclaim). Хэш по тексту увёл бы id и подвесил все пары.

## Фаза 5.7 — сверка

Идёт **до** синтеза, а не после. Расхождение с прошлым ресёрчем обязано попасть в отчёт; заметить его в фазе 7 значит заметить поздно.

```bash
python scripts/wiki_pair.py build --research-dir <root>/<slug>
```

**Префильтр (механический).** Пара вообще образуется, только если у claim'ов есть общая сущность И сопоставимый слот: совпадающая единица измерения либо достаточное пересечение содержательных токенов (Jaccard ≥ 0.34 после выкидывания имени сущности). Общей сущности мало: «Postgres популярен» и «Postgres 16 умеет логическую репликацию» сравнивать не с чем.

**Авто-вердикты (до модели).** Каждая ветка здесь — известный способ выдумать противоречие:

| Ситуация | Вердикт | Почему не конфликт |
|---|---|---|
| обе стороны с числами, `as_of` разошлись > 180 дней | `superseded` | цифра просто новее — это версия, а не спор |
| единицы не пересекаются (40% vs 40 млн) | `different-claim` | меряют разное |
| разошлись скоуп-квалификаторы (США/ЕС, медиана/среднее, enterprise/free, год) | `different-claim` | говорят о разном |

До адъюдикатора доходит только то, что пережило прескрин. Никакая уверенность модели не превратит устаревшую цену или другой регион в разногласие — у них просто нет туда пути.

**Адъюдикация.** Оставшиеся пары лежат в `<run>/.verify/wiki_pairs.json`. Вердикт — одно из четырёх: `same-claim-agree` · `same-claim-conflict` · `different-claim` · `unknown`. `unknown` — карантин: не согласие, не конфликт, в отчёт не идёт, через 90 дней линтер поднимает его как долг.

```bash
python scripts/wiki_pair.py record --research-dir <root>/<slug> --verdicts <file.json>
```

`record` **отклоняет всю пачку**, если конфликт заполнен односторонне. Конфликт без второго `as_of` неотличим от устаревшей цифры, без вторых корней — от одного источника, процитированного дважды. Такой «конфликт» попадёт в отчёт находкой, которой не заслужил.

**Что делать с подтверждённым конфликтом.** Это не дефект прогона. Две хорошо обоснованные позиции расходятся, потому что вопрос спорный — для этого в фазе 5 уже есть `dissent`. Новое здесь одно: расхождение стало видно МЕЖДУ прогонами, а не только внутри одного. Обе позиции идут в отчёт с обоснованием выбора, `confidence` не выше `medium`, а если арбитра нет — `contested`.

**Лимит.** Больше `MAX_ADJUDICATED = 40` пар — срез по свежести контрагента, и он **называется вслух** в выводе и в отчёте. Непроверенные пары ≠ отсутствие противоречий.

## Finish-up — запись

```bash
python scripts/wiki_ingest.py --research-dir <root>/<slug>
```

Детерминированно, без обращений к модели, **на любой глубине**. Shallow-прогон стоит ingest'а ровно ноль, а его источники переиспользуемы не хуже deep'овских; гейт по глубине лишил бы вики большей части входа и оставил 5.7 без базы для сравнения.

Пишет квитанцию `<run>/.verify/wiki_ingest.json`, и `validate_phases.py` её требует. Без гейта шаг, чей результат лежит вне папки прогона, тихо перестаёт выполняться — это уже случалось дважды с другими проверками.

Сущности берутся из `refresh_targets.md` §1. Нет файла — нет сущностей; из прозы никто ничего не выдумывает. Claim'ы цепляются к сущностям, уже известным вики, — консервативное направление: неизвестная сущность не даёт пар, выдуманная даёт неверные.

## Чтение перед стартом

```bash
python scripts/wiki_query.py --topic "<вопрос>"     # или --entity <name>, --stats
```

Отдаёт: сущности с прошлыми утверждениями, источники с готовой оценкой (не пересчитывать credibility с нуля), и главное — **открытые кросс-прогонные противоречия по теме**. Неразрешённое противоречие это готовый исследовательский вопрос, он идёт в `plan.md` без обсуждения.

## Линтер

```bash
python scripts/wiki_lint.py [--strict]
```

Сироты, битые `[[ссылки]]`, рёбра на несуществующие claim'ы, односторонние конфликты, протухший карантин. Гонять после ручной правки реестров и при подозрении на дрейф.

## Что НЕ делать

- Не редактировать страницы вики руками: правка живёт до следующего ingest. Спорное — в `pairs.jsonl`.
- Не объявлять конфликт, не показав обе стороны с их `as_of` и корнями.
- Не понижать `credibility` источника задним числом из-за одного прогона: страница копит максимум виденной оценки, расхождение — повод посмотреть, а не молча ухудшить страницу, на которую ссылаются другие.
- Не трактовать `unknown` как «сойдёт» — это карантин, как и в `authority.json`.
- Не молчать про срез по `MAX_ADJUDICATED`.
- Не заводить вики внутри проекта — смысл слоя в том, что он один на все ресёрчи.
- Не гейтить ingest по глубине.
